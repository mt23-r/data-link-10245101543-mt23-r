## 1. 原始接口提供什么数据？

原始接口在本实践中对应 `student_package/data/raw_states.json` 中的 OpenSky 离线状态向量。文件顶层包含批次时间 `time` 和状态数组 `states`。每条 `states` 记录是按固定索引排列的数组，而不是已经命名好的字典对象。

课程中重点使用的字段包括：`icao24` 目标标识、`callsign` 呼号、`time_position` 和 `last_contact` 时间、经纬度、气压高度和几何高度、`on_ground` 地面状态、速度、航向、垂直速度以及位置来源。它提供的是外部观测数据来源，不是 TeachingLink 帧，也不是最终态势结果。

## 2. 为什么原始数据不是完整态势结果？

原始数据只表示一批状态观测，尚未完成目标聚合、时间排序、航迹关联、当前态势筛选和质量检查。同一个目标可能在多时刻出现，原始记录也可能存在字段缺失、时间缺失或异常值。

完整态势需要在接收方得到可接收记录之后生成：先按 `target_id` 分组，再按 `timestamp` 排序形成航迹，最后为每个目标选择最新记录作为当前态势。因此，原始接口数据只是系统输入，不能直接当成“每个目标的最新状态表”。

## 3. 为什么发送方需要把内部状态封装成消息？

发送方内部状态适合程序处理，里面可以有字符串、布尔值、浮点数和 `None`。但通信双方需要的是稳定、明确、可校验的字节格式。TeachingLink 规定位置状态消息为固定 41 字节，每个字段都有固定偏移、长度、比例因子、偏置和标志位。

封装成消息后，接收方才能不依赖发送方程序内部结构，直接按协议解析字节流。封装还可以明确空值的表达方式，避免把缺失字段和真实 0 值混淆；同时通过 checksum、保留位和固定帧头发现消息损坏或格式错误。

## 4. 为什么接收方要检查长度、类型、校验和与保留位？

接收方检查长度，是为了确认一帧确实为 41 字节，避免截断、粘连或尾部残余数据导致解析错位。检查类型，是为了确认 `magic`、`version` 和 `message_type` 符合本课程的位置状态消息规范，避免把其他数据误当成本协议处理。

校验和用于发现传输或存储过程中的字节损坏。保留位用于确认发送方没有写入未约定的扩展信息，也能帮助发现位宽、偏移或编码错误。只有这些格式检查通过，`message_valid` 才能为 true；但 `message_valid` 只说明帧格式有效，不等于业务数据完全可靠。

## 5. CSV 与 SQLite 分别承担什么角色？

CSV 是本实践的主要成果格式，适合保存解码结果、校验日志、往返误差、航迹表和当前态势表。它便于人工检查，也便于用 Excel 或脚本重新读取，所以是必做路径。

SQLite 是选做的轻量级数据库路径，适合体验结构化持久化和 SQL 查询，例如按目标、时间范围查询接收记录。它可以帮助验证写入和读取的一致性，但本实践核心是协议解析、消息编解码、航迹生成、语义映射和一致性检查，因此 SQLite 不是必做前置条件。

## 6. 至少列出三个工程风险，并说明影响与处理方式。

| 工程风险 | 影响 | 处理方式 |
|---|---|---|
| 字段缺失与真实 0 值混淆 | 可能把缺失经纬度解释成 `(0,0)`，或把真实高度 0 m 当成空值，导致态势错误 | 发送方按字段是否存在设置 `validity_flags`；接收方先读有效位，无效字段恢复为 `None` |
| 接口时间缺失 | 无法确定记录时间，航迹排序和当前态势选择会失败 | 优先使用 `time_position`；缺失时回退 `last_contact` 并设置 `timestamp_fallback`；两者都缺失则记录必需字段缺失 |
| 消息损坏 | 坏帧可能产生错误目标、错误位置或程序异常 | 接收方逐帧检查长度、帧头、类型和 checksum；非法帧写入 `validation_log.csv`，跳过后继续处理 |
| 字节序或位宽不一致 | 多字节整数会被解释成错误数值，经纬度、高度和目标标识都可能失真 | 统一使用网络字节序（大端）；按规范固定偏移和长度编码；检查经纬度容器最高 2 位保留位 |
| 量化误差 | 浮点物理量编码为整数后不能完全恢复原值，影响精度判断 | 使用统一量化函数 `Q(y)=floor(y+0.5)`；在往返误差报告中检查误差是否不超过一个量化单位 |
| 存储失败或编码错误 | 后续模块无法读取 CSV/数据库，导致 M3-M6 阻断 | CSV 使用 UTF-8 with BOM；写入后重新读取验证；SQLite 作为选做，不让数据库失败阻断必做 CSV 流程 |
